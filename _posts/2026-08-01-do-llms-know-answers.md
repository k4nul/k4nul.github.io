## Summary / 요약

LLM의 답변을 볼 때 가장 먼저 버려야 할 오해는 “모델이 답을 어딘가에서 찾아서 꺼낸다”는 생각이다. 일반적인 생성 모델은 현재 입력과 이전에 생성한 토큰을 조건으로 다음 토큰의 확률 분포를 계산해 텍스트를 이어 간다. 이 과정은 검색 엔진의 문서 조회나 데이터베이스의 레코드 반환과 다르다.

이 차이를 이해하면 모델이 유용한 이유와, 그럴듯하지만 틀린 답을 낼 수 있는 이유를 함께 설명할 수 있다. 이 글은 LLM·검색·데이터베이스를 경쟁 기술로 비교하지 않고, 각자가 제공하는 증거와 실패 방식이 다르다는 점을 정리한다.

## Problem Statement / 문제 정의

“AI에게 물어봤더니 이렇게 답했다”는 문장은 답변의 출처와 신뢰도를 설명하지 못한다. 같은 문장이라도 다음 셋은 전혀 다른 방식으로 만들어질 수 있다.

1. 관계형 데이터베이스가 저장된 행을 조건에 맞춰 반환했다.
2. 검색 시스템이 문서 집합에서 관련 문단을 찾아 반환했다.
3. LLM이 입력 문맥을 바탕으로 다음 토큰을 생성했다.

첫 번째는 저장된 값의 일치 여부를, 두 번째는 검색 인덱스와 순위의 품질을, 세 번째는 모델·입력 문맥·생성 설정의 영향을 주로 받는다. 사용자가 셋을 모두 “AI의 지식”으로 부르면, 오류가 생겼을 때 어느 층을 점검해야 하는지도 흐려진다.

## Verified Facts / 확인된 사실

- Transformer는 attention 메커니즘에 기반한 신경망 구조로 제안되었다. 원 논문은 순환과 합성곱을 사용하지 않고 attention에만 기반한 구조를 제시한다.
  근거: [Vaswani et al., *Attention Is All You Need*](https://arxiv.org/abs/1706.03762)

- 생성형 모델의 API 요청에는 모델이 고려할 수 있는 입력 문맥의 한도가 있으며, 이 한도는 토큰으로 표현된다. OpenAI의 프롬프트 가이드는 관련 문맥을 요청에 추가하는 방식을 RAG라고 설명하면서, 모델이 생성 요청에서 고려할 수 있는 데이터에는 context window라는 한도가 있다고 명시한다.
  근거: [OpenAI Prompt engineering guide](https://developers.openai.com/api/docs/guides/prompt-engineering)

- RAG 연구는 사전학습된 생성 모델의 파라미터 메모리와 외부의 비모수적 메모리(문서 인덱스)를 결합하는 구조를 다뤘다. 이 논문은 지식 집약적 작업에서 외부 문서를 검색해 생성에 조건으로 넣는 접근을 제시했다.
  근거: [Lewis et al., *Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks*](https://arxiv.org/abs/2005.11401)

위 사실에서 바로 “LLM은 아무것도 모른다” 또는 “LLM은 데이터베이스보다 쓸모없다”는 결론이 나오지는 않는다. 모델은 요약, 변환, 초안 작성, 패턴 설명처럼 저장된 레코드를 그대로 돌려주는 것만으로는 해결하기 어려운 언어 작업에 유용하다. 다만 모델의 문장이 특정 문서·현재 규정·실제 거래 기록을 증명하지는 않는다.

## Reproduction Steps / 재현 순서

이 글의 목적은 특정 모델의 성능을 재현하는 것이 아니라, 답변의 근거 유형을 분리하는 것이다. 아래 표를 하나의 질문에 적용해 보면 된다.

| 질문 | 필요한 근거 | 우선 확인할 시스템 |
| --- | --- | --- |
| “우리 주문 번호 123의 상태는?” | 현재 저장값 | 데이터베이스 또는 업무 시스템 |
| “2026년 이후 이 제품 정책이 바뀌었나?” | 날짜가 있는 원문 | 검색·문서 조회와 출처 링크 |
| “이 정책을 고객 안내문으로 바꿔줘” | 입력으로 제공한 정책 문서 | LLM 생성 + 검토 |
| “이 두 문서의 차이를 표로 정리해줘” | 비교 대상 원문 | LLM 생성 + 원문 대조 |

실행 명령이나 특정 API 호출은 포함하지 않았다. 제품별 SDK와 모델명은 변할 수 있으며, 이 글의 결론은 특정 공급자의 구현에 의존하지 않는다.

## Observations / 관찰 결과

답변을 세 층으로 나누면 실패를 설명하는 문장도 달라진다.

- 데이터베이스 답이 틀렸다면: 저장값, 동기화 시점, 조회 조건을 확인한다.
- 검색 기반 답이 틀렸다면: 문서 최신성, 색인 상태, 검색어, 상위 결과를 확인한다.
- 생성 답이 틀렸다면: 입력 문맥, 지시, 모델 설정, 출력 검증 규칙을 확인한다.

특히 “출처를 달아 달라”는 요구는 생성 모델만으로 해결되지 않는다. 출처 링크는 실제 검색 결과나 제공된 문서의 식별자와 연결되어야 한다. 모델이 문장 끝에 URL처럼 보이는 문자열을 붙였다는 사실만으로는 근거가 생기지 않는다.

## Interpretation / 해석

내 해석으로는 LLM을 가장 잘 설명하는 비유는 ‘정답 저장소’보다 ‘문맥을 받아 언어 형태의 다음 행동을 제안하는 생성기’에 가깝다. 이 비유는 모델을 낮춰 보자는 뜻이 아니다. 오히려 모델이 무엇을 잘하는지 선명하게 만든다.

- 이미 확인된 사실을 읽기 쉬운 설명·표·초안으로 변환한다.
- 여러 입력을 비교하고, 사람이 검토할 수 있는 질문 목록을 만든다.
- 문서 검색이나 업무 시스템 조회의 결과를 사용자 언어로 연결한다.

반대로 최신 사실, 개인별 상태, 규정 준수 판단처럼 근거의 원문과 시점이 핵심인 작업은 생성 텍스트만 최종 증거로 삼기 어렵다. 이 경우 생성은 결과를 ‘말해 주는 층’이고, 사실의 근거는 별도 시스템에 남아 있어야 한다.

## Limitations / 한계

- LLM의 내부 표현과 특정 사실의 관계를 이 글만으로 단정할 수 없다. 모델·학습 데이터·추론 방식은 공급자마다 다르다.
- RAG는 최신 문서를 입력에 추가하는 한 방법일 뿐, 답변의 정확성·권한·인용 정확성을 자동 보장하지 않는다.
- 이 글은 특정 모델의 성능 비교나 벤치마크 결과를 제공하지 않는다.
- 의료·법률·금융처럼 고위험 판단이 필요한 분야에서는 해당 분야의 검증 절차와 책임 체계를 별도로 적용해야 한다.
