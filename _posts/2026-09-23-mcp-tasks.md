## Summary / 요약

CI, 대량 처리, 모델 학습, 승인 대기처럼 오래 걸리는 작업을 HTTP 연결 하나에 묶으면 timeout과 재접속 문제가 곧 업무 실패가 된다. MCP Tasks는 `io.modelcontextprotocol/tasks`라는 opt-in draft extension이다. client가 관련 요청에서 지원을 광고하고 server가 지원되는 `tools/call`을 task로 처리하기로 선택하면, 연결을 붙잡는 대신 durable `taskId`를 반환하고 client가 상태를 다시 조회·입력·취소할 수 있게 한다.

중요한 점은 task API가 장기 작업을 "성공"으로 만들어 주지 않는다는 것이다. 작업 상태, 외부 side effect, 취소, 결과 검증을 서로 다른 계약으로 설계해야 한다.

## Document Info / Environment

- 작성일·검증 기준일: 2026-09-07
- 문서 성격: specification analysis / operations guide
- 테스트 환경: 직접 구현·실행 없음. 공식 MCP Tasks 문서를 분석했다.
- 범위: 장기 실행 tool의 상태 모델. host별 지원 여부나 성능은 주장하지 않는다.

## Problem Statement / 문제 정의

`deploy_service`가 20분 뒤 끝난다고 하자. client가 연결을 잃었을 때 server는 작업을 잃으면 안 되고, client는 같은 배포를 새로 시작하면 안 된다. 승인이나 누락 입력이 생길 때도 "대기 중"과 "실패"를 구분해야 한다.

작업 API에는 적어도 네 개의 증거가 필요하다.

1. durable task가 생성됐다는 증거
2. 현재 상태와 필요한 다음 입력
3. 외부 작업이 실제로 수행한 상태 변경
4. 취소·실패 뒤의 정리 및 최종 결과

## Verified Facts / 확인된 사실

- MCP Tasks는 long-running MCP operation을 위한 opt-in draft 비동기 확장이다. server는 즉시 최종 결과 대신 durable task handle을 반환할 수 있다.
  근거: [MCP Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)
- client는 요청 metadata에서 Tasks 지원을 광고하고, server는 지원되는 요청을 task로 만들지 여부를 개별적으로 결정한다. capable client는 일반 결과와 `CreateTaskResult`를 모두 처리해야 한다.
  근거: [MCP Tasks extension specification](https://tasks.extensions.modelcontextprotocol.io/specification/2026-07-28/tasks)
- task 생성 응답 전 server는 task를 durable하게 생성해야 하며, 응답에는 `taskId`, 상태, `ttlMs`, `pollIntervalMs`가 포함될 수 있다.
  근거: [MCP Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)
- client는 `tasks/get`으로 조회하고, `input_required` 상태의 input request에 `tasks/update`로 응답할 수 있다.
  근거: [MCP Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)
- `tasks/cancel`은 cooperative cancellation이다. 성공 시 server는 빈 결과로 취소 의도를 acknowledge하며, 이후 상태는 eventually consistent하게 반영된다. 작업이 이미 완료됐거나 취소를 적용할 수 없으면 최종 상태가 `cancelled`가 아닐 수 있다. terminal state는 `completed`, `failed`, `cancelled`이다.
  근거: [MCP Tasks overview](https://modelcontextprotocol.io/extensions/tasks/overview)

## Reproduction Steps / 재현 순서

새 장기 작업을 다음 상태 계약으로 먼저 그린다.

```text
MCP task 상태:
working ↔ input_required
working | input_required → completed | failed | cancelled

애플리케이션 내부 사실(예: cancellation requested, provider cleanup, external side effect)은 별도 audit/workflow record로 관리한다.
```

그리고 각 상태에 답한다.

| 설계 질문 | 예시 |
| --- | --- |
| task ID는 무엇에 묶이는가? | 사용자·tenant·원래 요청 hash |
| TTL 뒤에는 무엇을 남기는가? | MCP task는 TTL 이후 failed 표시 또는 삭제될 수 있으므로, 별도 audit retention policy에 따라 감사용 요약과 외부 job ID |
| 입력은 무엇을 재확인하는가? | 승인자, 대상, 변경 요약 |
| 취소 후 무엇을 확인하는가? | 외부 provider 상태와 cleanup 결과 |
| 재시도는 무엇을 막는가? | 같은 deployment의 이중 시작 |

## Observations / 관찰 결과

task status는 tool 서버가 아는 상태이고, business outcome은 외부 시스템이 보장하는 상태다. 예를 들어 `cancelled`가 되어도 provider가 이미 이메일을 보내거나 배포를 시작했을 수 있다. 반대로 `completed`여도 사용자가 기대한 리전에 배포됐는지는 별도 검증이 필요하다.

따라서 final result에는 단순한 문장 대신 target ID, external job ID, 관찰 시각, 최종 확인 방법을 넣는 편이 낫다. failure에는 재시도 가능 여부와 이미 발생한 side effect를 함께 남겨야 한다.

## Interpretation / 해석

MCP Tasks는 "긴 요청을 polling으로 바꾸는 기능"보다 **재개 가능한 업무 상태를 API 계약으로 만드는 도구**에 가깝다. 좋은 tool은 task ID만 돌려주지 않는다.

```text
task identity + owner check + state transition
+ input/approval record + external outcome evidence
+ cancellation and retry policy
```

이 요소가 없으면 task는 UI spinner를 유지하는 용도에 그치고, 장애 뒤에 무엇이 실행됐는지 판단하지 못한다.

## Limitations / 한계

- 이 글은 MCP Tasks 공식 문서 분석이며 상용 host의 구현 지원을 테스트하지 않았다.
- Tasks는 검증 기준일 현재 draft extension이며, client와 server의 명시적 opt-in이 필요하고 wire format·동작이 바뀔 수 있다.
- cooperative cancellation은 rollback 또는 외부 side effect 제거를 보장하지 않는다.
- MCP에서 `failed`는 execution 중 JSON-RPC error를 뜻한다. tool 결과의 `isError: true`는 `completed` task result에 포함될 수 있으므로, 제품의 업무 실패 분류와 MCP task status를 동일시하면 안 된다.
- durable task store는 개인정보 보존 기간, tenant isolation, 접근 제어 정책을 별도로 요구한다.
- task 상태만으로 사용자의 업무 목표가 달성됐다고 단정할 수 없다.
